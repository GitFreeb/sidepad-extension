# CLAUDE.md — Проектные инструкции

Инструкции для Claude Code при работе с данным проектом.

## Правила работы

- После каждого изменения логики, архитектуры или поведения расширения — **сразу обновлять этот файл**: добавлять или корректировать соответствующий раздел в «Ключевых архитектурных решениях».
- Не ждать отдельной просьбы от пользователя — обновление инструкций является частью каждой задачи.

## Описание проекта

Chrome-расширение (Manifest V3) — боковая панель с чек-листом задач для повседневного приминения. Открывается как Side Panel при клике на иконку в панели браузера.

## Установка расширения

1. Открыть `chrome://extensions`
2. Включить **Режим разработчика** (переключатель вверху справа)
3. Нажать **Загрузить распакованное расширение** → выбрать папку `Sidepad/`
4. После изменений в JS/HTML/CSS нажать кнопку перезагрузки на карточке расширения

Шаг сборки отсутствует — чистый vanilla JS, без бандлера и зависимостей.

## Архитектура

Все файлы расширения находятся в `Sidepad/`:

- `manifest.json` — Manifest V3; разрешения `sidePanel` и `storage`
- `background.js` — service worker; при установке задаёт `openPanelOnActionClick: true`
- `popup.html` / `popup.css` — интерфейс боковой панели
- `popup.js` — вся логика (состояние, хранилище, рендеринг, импорт)

`Sidepad/default.md` — эталонный формат пустого списка по умолчанию; `DEFAULT_TASKS` в `popup.js` — пустой массив `[]`.

## Ключевые архитектурные решения

**Конвенция ID задач:** встроенные задачи имеют `id ≤ 10000`; пользовательские — `id = Date.now() + 10001` (всегда `> 10000`). Кнопки удаления только для `id > 10000`; «Сбросить выполненные» переводит встроенные задачи в невыполненные, а не удаляет.

**Сохранение состояния:** `chrome.storage.local` хранит `{ tabs, activeTabId, lightMode, lang }`. При загрузке восстанавливаются все вкладки, активная вкладка, тема и язык. `tab.autoSave` персистится вместе с остальными полями вкладки, но безусловно сбрасывается в `false` при каждой загрузке — эффективно не переживает сессию, хотя технически какое-то время лежит в хранилище (см. раздел «Автосохранение» ниже).

**i18n:** константа `I18N` в `popup.js` содержит строки для `ru` и `en`. Дефолтный язык — `en`. Функция `tr(key)` возвращает строку текущего языка. `applyLang(l, save)` обновляет DOM и сохраняет выбор. Переключатель `RU`/`EN` находится в `.tabbar-actions` рядом с кнопкой темы.

**Импорт файлов — `parseMd(content, fileName)`:** авто-определяет формат файла и выбирает парсер:
- **Markdown** (есть строки `- ` или `* `) — заголовки `##` становятся секциями, строки `- `/ `* ` → задачи, `[x]`/`[ ]` → done-флаг. URL извлекаются регулярным выражением.
- **Plain text** (fallback, нет `-`/`*` буллетов) — поддерживает:
  - Нумерованные списки: `1. задача`, `1) задача`
  - Буллеты `*` / `•`
  - Заголовки-секции: строка, за которой `---`/`===` (setext); строка целиком заглавными буквами (≥2 капитальных, ≤60 символов, нет URL); строка, заканчивающаяся на `:` (≤60 символов, нет URL)
  - Признаки выполненной задачи: `[x]`, `✓`, `✔`
  - Обычные строки → задачи в текущую секцию

**Рендеринг:** `render()` полностью перестраивает `innerHTML` при каждом изменении состояния. XSS предотвращается через `escapeHtml()`.

**Секции — имена и приоритет:** внутренний ключ `__default__` удалён. Все секции — обычные строки. Дропдаун показывает плейсхолдер «Выбор секции»/«Select section»; `selectedSection = null` означает ничего не выбрано. При добавлении задачи приоритет секции: 1) выбранная в дропдауне, 2) текст в поле «новая секция», 3) автоимя «Новая секция N»/«New section N» (первый свободный номер). `getNextSectionName(existingSections)` ищет первый свободный номер. `LEGACY_DEFAULT_SECTIONS` — набор `{'__default__', 'Дополнительные задачи', 'Extra tasks'}` для миграции старых данных; `migrateDefaultSection(tab)` конвертирует их при загрузке.

**Автосохранение — `tab.autoSave` (per-tab, не персистится):** управляется кнопкой `↓auto` (`#autoSaveBtn`, `.btn-auto-save`) в `.tabbar-actions`. Раньше был глобальным флагом в `chrome.storage.local`; теперь это свойство конкретной вкладки (`tab.autoSave`, boolean), которое **не сохраняется** между сессиями — при каждом `loadAll()` у всех вкладок принудительно `false`, независимо от прошлого состояния. Кнопка в тулбаре одна, но отражает и переключает состояние активной вкладки (`applyAutoSaveButton(tab)` вызывается при каждой смене активной вкладки — `switchTab`, `closeTab`, `loadAll`, `applyImportedFile`, `switchToOrCreateDefault`, `loadExample`).

Вкладка `example` исключена из автосохранения полностью — обработчик клика на `#autoSaveBtn` выходит сразу (`if (!tab || tab.title === 'example') return;`), ещё до проверки текущего состояния `tab.autoSave`: на этой вкладке `↓auto` невозможно включить ни при каких условиях (спецификация: «Вкладка `example` — никогда не экспортируется и не участвует»).

Клик по `↓auto` для включения — асинхронный (`popup.js`, обработчик на `#autoSaveBtn`): если у вкладки уже есть сохранённый `FileSystemFileHandle` (см. ниже), тихо переподтверждает permission (`handle.queryPermission`/`requestPermission({mode: 'readwrite'})` — сам клик даёт нужный user gesture); если handle ещё нет — открывает `showSaveFilePicker({startIn: 'documents', ...})` и сохраняет выбранный handle. Отказ/отмена оставляет `autoSave` выключенным. Выключение — просто `tab.autoSave = false` и остановка синхронизации (см. ниже). В браузерах без File System Access API (`!window.showSaveFilePicker`, например Brave с выключенным флагом) — включение работает как простой toggle, без запроса handle и без живой синхронизации. Если сразу после выбора файла в пикере `startSync(tab, handle)` не смог прочитать `handle.getFile()` (файл стал недоступен и т.п.) — возвращает `false`, обработчик молча `return`, `tab.autoSave` остаётся `false`, кнопка `↓auto` остаётся выключенной без какого-либо `alert()` (только `console.error`); при этом выбранный handle уже успел сохраниться в IndexedDB через `setStoredHandle`, поэтому следующий клик пропускает пикер и сразу идёт на проверку permission.

Поведение при **autoSave = ON** (правила по типу вкладки, источник флага — `tab.autoSave` вместо прежнего глобального):
- `example` — никогда: ни диалог, ни сохранение.
- `default` — без диалога; сохраняется только если `tasks.length > 0`.
- Любой пустой список — ни диалога, ни сохранения.
- Остальные вкладки с задачами — диалог подтверждения + сохранение.

Поведение при **autoSave = OFF**:
- `example` и `default` — без диалога, без сохранения.
- Импортированные с задачами — диалог «закрыть без сохранения?» → закрыть; без сохранения.
- Пустые — без диалога, без сохранения.

**Порядок секций в markdown — `generateMd(taskList, titleStr, sectionsList)`:** секции в файле пишутся в порядке `sectionsList` (по умолчанию — глобальный `sections`), а не в порядке первого появления в `taskList` — это тот же порядок, что использует `render()` для экрана (`orderedSections = [...sections]`, затем любые «бесхозные» секции из задач впристрой). Раньше секция бралась из плоского массива задач: при создании задачи в новой секции `sections.unshift(name)` кладёт секцию наверх экрана, но `tasks.push(newTask)` кладёт саму задачу в конец массива — из-за этого экспортированный файл писал новую секцию последней, а `parseMd()`+`deriveSections()` на другой стороне (обычный импорт или живая синхронизация) восстанавливали её тоже в конце, хотя на экране она была наверху. Воспроизводилось в обе стороны синхронизации, т.к. асимметрия не зависит от направления. `writeTabToHandle` передаёт `tab.sections`; оба вызова `autoSaveMdData` (из `closeTab` и `autoSaveMd()`) передают соответствующий `sections`-массив четвёртым аргументом; вызовы `generateMd()` без аргументов в `exportBtn` не тронуты — там и так используется активный глобальный `sections` по умолчанию.

**Запись через handle, без меток времени:** `autoSaveMdData(tabId, taskList, titleStr, sectionsList)` (асинхронная) — если для `tabId` есть сохранённый `FileSystemFileHandle` (IndexedDB, см. ниже), пишет напрямую через `handle.createWritable()`, перезаписывая тот же файл. Если handle нет — fallback: `chrome.downloads.download({saveAs: false, conflictAction: 'overwrite'})`, тоже без диалога. **Метка времени в имени файла (`title_YYYY-MM-DD_HH-MM.md`) убрана полностью** — не прижилась у пользователя, оба пути (через handle и fallback) теперь просто перезаписывают файл с постоянным именем. `taskList`/`titleStr` передаются как отдельные аргументы, а не читаются из живого объекта вкладки — иначе в сценарии «закрытие последней вкладки» (`closeTab`, сброс в `default` сразу после вызова) асинхронная запись могла бы захватить уже сброшенные (пустые) данные вместо тех, что были на момент закрытия.

**Хранение файлового handle — IndexedDB:** `FileSystemFileHandle` не сериализуется в `chrome.storage` (не JSON), но сериализуется structured-clone в IndexedDB. `getStoredHandle(tabId)`/`setStoredHandle(tabId, handle)`/`deleteStoredHandle(tabId)` — object store `handles` в базе `sidepad-handles`, ключ — `tab.id`. Заполняется при первом ручном «Экспорт» для вкладки (`exportBtn`-обработчик) или при первом включении `↓auto`. Удаление (`stopSync` + `deleteStoredHandle`) вызывается в пяти местах: в обеих ветках `closeTab` (сброс последней оставшейся вкладки в `default` и обычное удаление вкладки) и в ветке удаления вкладки у `clearDoneBtn`, а также — поскольку `applyImportedFile()` и `loadExample()` тоже могут молча удалить вкладку `default`, если создают новую вкладку ей на замену, — в начале обеих этих функций, для той заменяемой вкладки. Handle переживает только переключение/выключение `autoSave`, не переживает удаление самой вкладки.

**Кросс-браузерная синхронизация:** пока `↓auto` включён на вкладке (и File System Access API доступен), работают два независимых цикла, ключ состояния — `syncState` (`Map<tabId, {handle, pollTimer, writeTimer, lastKnownMtime}>`):
- **Чтение** — `pollTab(tabId)`, `setInterval` каждые 2000 мс: сравнивает `handle.getFile().lastModified` с последним известным; при расхождении перечитывает файл, парсит через `parseMd()`, обновляет `tab.tasks`/`tab.sections` (и видимые `tasks`/`sections` + `render()`, если это активная вкладка). Гард `busyEditing()` (`tabId === activeTabId && (editingId !== null || renamingSection !== null || moveMenuTaskId !== null || dragType !== null)`) проверяется **дважды**: один раз в начале функции, до `handle.getFile()`, и второй раз сразу после `await file.text()`, перед разбором и применением — пользователь может успеть начать инлайн-правку, переименование секции или drag именно во время этих `await`-ов, уже после того как первая проверка прошла. Причина гарда: `parseMd()` генерирует новый `id` для каждой задачи при каждом разборе markdown и не сохраняет id между раундами; если бы чужое изменение применилось поверх открытой инлайн-правки, `editingId` осиротел бы (указывал бы на уже не существующий в свежем массиве id), и `saveEdit()` молча потерял бы недописанную правку пользователя (паттерн `tasks.map(t => t.id === id ? ... : t)` там — тихий no-op при промахе, без ошибки); `dragType !== null` добавлен в гард по той же логике, что и уже описанный для drag вкладок хазард — поллинговый `render()` посреди drag отрывает перетаскиваемый `<li>` от DOM без единого `dragend`. При срабатывании любой из двух проверок применение откладывается целиком: `state.lastKnownMtime` продвигается **только после успешного применения** (`parsed`/`tab.tasks`/`tab.sections` уже обновлены), а не сразу после чтения `file.lastModified` — если гард сработал вторым разом, либо `file.text()`/`parseMd()` бросили исключение, мтайм остаётся прежним, и та же ревизия файла будет повторно предложена на следующем цикле опроса (через 2 с), а не потеряна навсегда. Персистится через `saveAllTabs()` напрямую, **не** через `saveTasks()` — иначе применение чужого изменения тут же спровоцировало бы запись обратно в файл. У вызова `resetCollapsedState()` внутри `pollTab` (для активной вкладки) нет пары `allCollapsed = false; updateCollapseBtn();`, в отличие от всех остальных мест файла, где вызывается `resetCollapsedState()` — если пользователь до этого нажал «Свернуть», применение удалённого изменения через poll заново раскрывает секции, но кнопка может остаться с устаревшей надписью «Развернуть», пока её не обновит что-то другое.
- **Запись** — `scheduleSyncWrite(tab)`, вызывается из `saveTasks()` (единственная точка входа для правок активной вкладки) при каждом изменении, debounce 1500 мс, затем `writeTabToHandle(handle, tab)`. Ошибка записи, отличная от `NotFoundError`/`NotAllowedError`/`SecurityError` (например, временная ошибка диска/квоты), не ретраится и никак не сообщается пользователю — просто отбрасывается до следующей реальной правки, которая заново вызовет `scheduleSyncWrite`. `state.lastKnownMtime` при неудачной записи не продвигается, поэтому файл и представление расширения о нём не расходятся молча — но именно та неудавшаяся правка проактивно не переотправляется.
- `startSync(tab, handle)`/`stopSync(tabId)` — запускаются/останавливаются кликом по `↓auto`, а не переключением вкладок: синхронизация фоновых (неактивных) вкладок продолжает работать, пока их собственный `autoSave` включён. `startSync` перед установкой `pollTimer` читает и парсит текущее содержимое файла, но применяет его к вкладке только при `parsed.length > 0` (`tab.tasks`/`tab.sections`, и видимые `tasks`/`sections` + `resetCollapsedState()` + `render()`, если вкладка активна, плюс `saveAllTabs()`) — этот гард в точности повторяет паттерн `if (!imported.length) return;`, уже используемый в `applyImportedFile()` и `loadExample()`. Причина: пустой/только что созданный файл (типичный сценарий — клик по `↓auto` на вкладке без handle, пользователь создаёт новый файл в пикере) не должен молча затирать реальный список вкладки пустым `[]`, с немедленной фиксацией потери через `saveAllTabs()`. `lastKnownMtime`, запись в `syncState` и запуск `pollTimer` происходят безусловно, вне зависимости от того, применился ли разбор — синхронизация всё равно активируется, а дальнейший опрос (`pollTab`) подхватит реальное содержимое, как только оно появится в файле (с любой стороны). Для файла, в котором уже есть контент (обычный случай подключения к существующему синк-файлу), содержимое применяется сразу — но только если оно **совпадает** с тем, что уже на экране, либо вкладка была пустой (см. следующий пункт про защиту от дурака). Этот гард `parsed.length > 0` действует только в момент активации, внутри `startSync`. Пока синхронизация уже идёт, `pollTab` применяет содержимое файла безусловно, включая пустой результат разбора — если файл на диске легитимно опустел (сознательная чистка на другой стороне или, после исправления `generateMd`, экспорт пустого списка), вкладка тоже очищается и это сразу фиксируется через `saveAllTabs()`. Это осознанное поведение, а не пробел: во время активной синхронизации файл считается источником истины, и настоящее удаление всех задач на другой стороне должно долетать, а не тихо игнорироваться; защита от затирания есть только в один момент — при самой первой активации, чтобы отличить «файл только что создан и в нём пока ничего нет» от «кто-то всё удалил».
- **Защита от дурака при активации:** если у вкладки уже есть реальные задачи (`tab.tasks.length > 0`) и выбранный/переподтверждённый файл содержит ДРУГОЙ список, `startSync` не подменяет экран молча — сравнивает содержимое через `generateMd(tab.tasks, tab.title, tab.sections)` против `generateMd(parsed, tab.title, deriveSections(parsed))` (та же функция, что пишет на диск, отдельной логики сравнения нет) и, если строки различаются, показывает `confirm(tr('syncMismatchConfirm'))` с числом задач по обе стороны. Отказ = `startSync` возвращает `false`, активация откатывается целиком (как отмена пикера) — ничего не применяется, `autoSave` не включается. Пустая вкладка или совпадающее содержимое пропускают диалог. Отдельно: пикер для подключения к ещё-не-настроенной вкладке (`getStoredHandle` вернул `null`) — сознательно `showOpenFilePicker` («Открыть») + явный `requestPermission({mode: 'readwrite'})` после, а не `showSaveFilePicker` («Сохранить как»). У диалога сохранения нативное окно ОС при выборе существующего файла спрашивает «Заменить файл?», хотя на этом шаге код только читает, ничего ещё не пишет — формулировка провоцирует случайную перезапись чужого списка пустым (человеческая ошибка, зафиксированная на практике). Создание НОВОГО файла для вкладки по-прежнему идёт через кнопку «Экспорт» (её `showSaveFilePicker` не тронут) — `↓auto` дальше просто переиспользует сохранённый ею handle без повторного выбора.
- **Переименование вкладки `default` при подключении к чужому файлу:** если у активной вкладки `tab.title === 'default'` и она подключается через `↓auto` к handle (свежевыбранному через `showOpenFilePicker` или уже сохранённому — проверяется в обеих ветках), вкладка переименовывается под имя файла (`handle.name` без `.md`) — `tab.title = newTitle; applyTitle(newTitle); renderTabs(); saveAllTabs();`, тем же способом, каким `applyImportedFile()` уже называет новую вкладку по имени импортируемого файла. Найдено и подтверждено по логам на практике: без переименования вкладка визуально показывает чужой синхронизируемый список, но внутренне остаётся `'default'` — из-за этого продолжают действовать специальные правила default-вкладки (например, более мягкое подтверждение при «✕ очистить»), хотя в ней уже реальные данные, а `generateMd()` при каждой записи пишет `# default` в заголовок файла вместо его настоящего имени, из-за чего заголовок файла «плавает» между инстансами в зависимости от того, кто последний писал. Проверка в обеих ветках (не только при свежем выборе файла) самоисправляет вкладки, уже застрявшие в этом состоянии до появления фикса — не требует от пользователя ручного переименования.
- Повторный «Экспорт» в другой файл, пока вкладка активно синхронизируется (`syncState.has(activeTabId)`), не просто обновляет сохранённый в IndexedDB handle — обработчик `exportBtn` СНАЧАЛА пишет в новый handle текущий `generateMd()` (то, что реально на экране) и лишь ПОСЛЕ завершения записи, если вкладка была синхронизируемой, перезапускает `startSync(tab, handle)` на этот же handle. Порядок обратный тому, что могло бы показаться логичным: `startSync` применяет содержимое файла к вкладке, поэтому если бы он выполнялся до записи, он подменял бы видимый список содержимым старого/чужого файла — и именно эта (неверная) подмена затем ушла бы в `generateMd()` при записи. Запись первой гарантирует, что в файл уходит именно текущий список пользователя, а не содержимое файла, в который экспортируют; последующий `startSync` читает обратно ровно то, что только что было записано — самосогласованно, без «моргания» и без риска подмены. Если перезапущенный `startSync` вернул `false` (например, файл стал недоступен сразу после выбора) — обработчик явно выставляет `tab.autoSave = false` и вызывает `applyAutoSaveButton(tab)`, чтобы кнопка `↓auto` не осталась во «включённом» состоянии при фактически мёртвой синхронизации (сам `startSync` уже вызвал `stopSync` внутри себя при неудаче, повторный вызов не нужен).
- Файл удалён/недоступен или permission отозван в процессе работы — оба обработчика ошибок (в `pollTab` и в debounce-таймере `scheduleSyncWrite`) реагируют не только на `NotFoundError` (файл удалён/перемещён), но и на `NotAllowedError`/`SecurityError` (permission отозван, пока синхронизация уже активна) — во всех трёх случаях `stopSyncWithAlert(tabId)`: останавливает синхронизацию, выключает `autoSave` для вкладки, один `alert()`. Без расширения до `NotAllowedError`/`SecurityError` отозванное разрешение приводило бы к бесконечному тихому повтору ошибки каждые 2 с, при этом кнопка `↓auto` продолжала бы показывать включённое состояние, хотя синхронизация уже мертва.
- Работает только между инстансами, где обе стороны независимо включили `↓auto` и указали один и тот же файл — расширение не знает и не может узнать состояние другого браузера напрямую, обмен идёт только через содержимое файла на диске.

**Известные ограничения синхронизации (осознанные компромиссы, не баги):**
- **Last-writer-wins без merge, в узком окне гонки:** если удалённое изменение приходит, пока у пользователя открыта незавершённая инлайн-правка, `pollTab` откладывает его применение целиком (см. выше). Если пользователь завершает правку до того, как следующий цикл опроса подхватит отложенное изменение, возникает гонка между (а) дебаунсенной записью собственной правки (`scheduleSyncWrite`, срабатывает через 1500 мс после `saveTasks()`) и (б) следующим циклом опроса (срабатывает по своему независимому расписанию 2000 мс). Кто сработает раньше — тот и побеждает: если раньше уйдёт локальная запись, файл (и `lastKnownMtime`) отразят локальную правку, а всё ещё отложенное удалённое изменение так и не применится (молча вытесняется). Если раньше сработает опрос — удалённое содержимое заменит `tab.tasks`, а всё ещё не сработавший колбэк записи (хранящий ссылку на уже подменённый объект `tab`) затем запишет это удалённое содержимое обратно в файл — тогда теряется только что завершённая локальная правка. Это неизбежное следствие отсутствия merge-логики (осознанно вне рамок задачи), а не баг.
- Есть узкое временное окно между завершением `write()`/`close()` в `writeTabToHandle` и разрешением подтверждающего вызова `handle.getFile()` (которым обновляется `state.lastKnownMtime`), в течение которого тик опроса может застать файл и ошибочно принять только что записанные расширением же данные за внешнее изменение — и повторно их применить (безвредно по содержимому, поскольку оно идентично, но вызывает заметный визуальный «моргание»/лишний `render()` и сбрасывает `collapsedSections`).

**Кнопка «✕ очистить» — поведение по типу вкладки:**
- `default` — очищает содержимое, таб остаётся; если автосохранение включено и есть задачи — диалог подтверждения (`clearConfirm`) → при подтверждении автосохранение, затем очистка; отказ от диалога оставляет список как есть. Без диалога, если автосохранение выключено или список уже пуст.
- `example` — закрывает таб и переключается на `default`; без диалога, без сохранения.
- Импортированные вкладки — диалог подтверждения (если задачи есть) → автосохранение → закрывает таб → переключается на `default`.
- Если вкладка `default` не открыта — создаётся автоматически (`switchToOrCreateDefault()`).

**Индикатор скрытых вкладок:** `.tab-strip` обёрнут в `.tab-strip-wrap` (flex: 1, position: relative, overflow: hidden). CSS `::after`/`::before` дают градиентный fade вправо/влево при классах `overflow-right`/`overflow-left`. Два бейджа: `#tabOverflow` (`.tab-overflow-right`) — справа, `#tabOverflowLeft` (`.tab-overflow-left`) — слева. Считаются только полностью невидимые вкладки (частично обрезанные — нет). Правый бейдж: вкладка считается скрытой, если её левый край уже за `visibleEnd - 2`; клик скроллит на 70% вперёд. Левый бейдж: вкладка считается скрытой, если её правый край левее `scrollLeft + 2`; клик делает `scrollTo({ left: 0 })`. `updateTabOverflow()` вызывается из `renderTabs()`, scroll-листенера и ResizeObserver. После перестройки HTML активная вкладка прокручивается в видимую зону через `scrollIntoView`.

**Перемещение задачи в другую секцию:** кнопка `→` (`.btn-move`, `data-action="move-task"`) появляется при наведении на задачу, если существует хотя бы одна другая секция. Клик → `moveMenuTaskId = id` → `render()` генерирует `<ul class="move-section-menu">` с секциями (кроме текущей) прямо в `<li>` задачи, затем позиционирует меню через `position: fixed` и `getBoundingClientRect()` (чтобы оно не обрезалось overflow родителя). Выбор секции вызывает `moveTaskToSection(id, section, 'start')` — задача вставляется в начало целевой секции. Drag-and-drop на заголовок секции вызывает `moveTaskToSection` без параметра (дефолт `'end'`) — вставляет в конец. `Escape` или клик вне меню закрывает его через document click handler. `moveMenuTaskId` сбрасывается при переключении и закрытии вкладки.

**Переименование секции:** кнопка `✎` (`.btn-rename-section`, `data-action="rename-section"`) появляется при наведении на шапку секции. Клик → `renamingSection = name` → `render()` рендерит `<input class="section-rename-input">` вместо `<span class="section-title">`. `Enter`/`blur` → `finishSectionRename()`: обновляет `section` у всех задач и массив `sections`, дедуплицирует. Если новое имя совпадает с существующей секцией — задачи сливаются. `Escape` → отмена. Состояние `renamingSection` сбрасывается при переключении и закрытии вкладки.

**Кнопка «Свернуть / Развернуть»** (`#collapseAllBtn`) в тулбаре: флаг `allCollapsed` (`let allCollapsed = false`). Нажатие «Свернуть» добавляет все секции в `collapsedSections`, флаг → `true`, кнопка меняет текст на «Развернуть». Нажатие «Развернуть» вызывает `resetCollapsedState()` (оставляет свёрнутыми только полностью выполненные секции), флаг → `false`. `updateCollapseBtn()` синхронизирует текст кнопки с флагом. Флаг сбрасывается в `false` при переключении и закрытии вкладки.

**Две функции управления свёрнутым состоянием:**
- `resetCollapsedState()` — полный сброс `collapsedSections`: очищает и заново добавляет только секции, где все задачи выполнены. Вызывается при смене/закрытии вкладки, загрузке, импорте, нажатии «Развернуть».
- `syncAutoCollapse()` — неразрушающая: только *добавляет* секции с выполненными задачами, не трогает ручные свёртки. Вызывается при drag-and-drop, добавлении/удалении задач, чекбоксе. Это гарантирует сохранение ручного состояния при перетаскивании секций.

**Оповещение об обновлениях:** расширение распространяется только как unpacked (без Chrome Web Store), поэтому проверка обновлений реализована вручную в `popup.js`. При каждом открытии панели `loadAll()` вызывает `checkForUpdate()`: сравнивает `chrome.runtime.getManifest().version` с полем `version` из `manifest.json` ветки `main` на GitHub (`MANIFEST_RAW_URL`, числовое сравнение через `compareVersions`). Результат кэшируется в `chrome.storage.local.updateInfo = { lastChecked, latestVersion, dismissedVersion }`, повторный сетевой запрос — не чаще раза в `UPDATE_CHECK_INTERVAL_MS` (24 часа), независимо от успеха/неудачи запроса. Если доступна более новая версия — `renderUpdateBanner()` показывает баннер `#updateBanner` (между tabbar и breadcrumb). Клик по баннеру открывает `REPO_URL` на GitHub; крестик скрывает баннер (`dismissedVersion = latestVersion`) до выхода следующей версии. Бейдж на иконке расширения (`chrome.action.setBadgeText`) не используется — минимальный размер бейджа задаёт сам Chrome, и на маленькой иконке он выглядит слишком грубым; решили оставить только баннер.

**Импорт/экспорт в Brave (fallback без File System Access API):** Brave по умолчанию отключает `window.showOpenFilePicker`/`showSaveFilePicker` (флаг `brave://flags/#file-system-access-api`), из-за чего в Chrome-based браузерах без этого API кнопки импорта/экспорта не работали — исключение молча уходило в `console.error`. Оба обработчика теперь проверяют наличие API через `if (!window.showOpenFilePicker)` / `if (!window.showSaveFilePicker)` и используют fallback: импорт — скрытый `<input type="file" id="importFileInput" accept=".md,.txt" hidden>` в `popup.html`. Логика разбора/применения импортированного файла вынесена в `applyImportedFile(text, fileName)`, общую для обоих путей (File System Access и `<input type="file">`).

Экспорт в fallback-режиме (без `showSaveFilePicker`) использует `chrome.downloads.download({ url, filename, saveAs: true, conflictAction: 'overwrite' })` (разрешение `downloads` в `manifest.json`), а не `<a download>`. Причина: `<a download>` не умеет перезаписывать — браузер всегда доуникальнивает совпадающее имя файла (`name (1).md`, `name (2).md`, ...), тогда как в Chrome (где `showSaveFilePicker` доступен) повторный экспорт с тем же именем реально перезаписывает файл через File System Access API. `conflictAction: 'overwrite'` убирает доуникальнивание имени. `saveAs: true` обязателен: `saveAs: false` заставляет `chrome.downloads` писать строго в папку «Загрузки» по умолчанию, полностью игнорируя ранее выбранную папку (запись API вне папки «Загрузки» без интерактивного диалога заблокирована на уровне Chrome/Brave — это ограничение платформы, не то, что можно обойти кодом).

**Важное ограничение, подтверждённое на практике в Brave:** даже с `saveAs: true` диалог `chrome.downloads.download()` каждый раз открывается в дефолтной папке «Загрузки» (`brave://settings/downloads`), а не в последней реально выбранной пользователем папке — в отличие от обычного `<a download>`, который эту память наследует от ОС/браузера, но не умеет перезаписывать. Одновременно и память папки, и перезапись через `chrome.downloads` в Brave получить нельзя — это два взаимоисключающих режима одного и того же API. Полноценное решение — тот же File System Access API, что и в Chrome (`showSaveFilePicker` + `lastFileHandle`), который в Brave выключен по умолчанию флагом `brave://flags/#file-system-access-api`. Пользователю рекомендовано включить этот флаг вручную — тогда Brave полностью переходит на основную (не fallback) ветку экспорта и получает то же поведение, что и в Chrome, без изменений в коде. `chrome.downloads`-fallback остаётся как есть — для случаев, когда флаг не включён (даёт `conflictAction: 'overwrite'`, но не даёт памяти папки). `autoSaveMdData()` (автосохранение, см. выше) использует другой fallback: `chrome.downloads.download({saveAs: false, conflictAction: 'overwrite'})` с постоянным именем файла (`title + '.md'`, без таймстемпа) — метка времени в имени убрана вместе с самим автосохранением по расписанию (см. раздел «Автосохранение» выше). Ручной «Экспорт» (Chrome/FSA-ветка) также сохраняет полученный handle в IndexedDB под id активной вкладки (`setStoredHandle`) — это тот же механизм хранения, что использует кросс-браузерная синхронизация (см. выше), поэтому включение `↓auto` для вкладки, которую уже хоть раз вручную экспортировали, не потребует повторного выбора файла.

MIME-тип всех сохраняемых `Blob` — `text/markdown`, а не `text/plain` (тот же ключ используется и в `accept` для `showSaveFilePicker`). Раньше был `text/plain`: имя файла корректно заканчивалось на `.md` (это гарантирует `applyTitle()`), но ОС/браузер определяли содержимое как обычный текстовый файл (TXT), а не Markdown — именно MIME-тип, а не расширение, некоторые файловые менеджеры и диалоги показывают как «тип файла». Импорт (`showOpenFilePicker`, строка ~604) сознательно остаётся на `text/plain` с `['.md', '.txt']`, т.к. должен принимать оба формата.

**Drag-and-drop вкладок:** `.tab` в `#tabStrip` — `draggable="true"` (кроме вкладки в режиме переименования: `draggable="false"`, как и у `.tab-close`/`.tab-rename-input`, чтобы клик по крестику или работа с полем не запускали drag). Переупорядочивание переиспользует существующий паттерн drag-and-drop задач/секций: общие глобальные `dragType`/`dragId` (новое значение `dragType = 'tab'`) и общий хелпер `clearDragUI()`. Отдельный IIFE на `#tabStrip` ориентируется по `clientX` (вкладки расположены горизонтально, в отличие от вертикального списка задач), индикатор позиции — вертикальная линия слева/справа от вкладки-цели (`.tab.drag-before`/`.tab.drag-after`), а не горизонтальная, как у задач. `moveTab(sourceId, targetId, pos)` переставляет элементы только в массиве `tabs` — `activeTabId`, `tasks`, `sections` не затрагиваются. Результат сохраняется через `saveAllTabs()`. Авто-скролл при перетаскивании к краю: пока курсор в зоне `EDGE_ZONE` (32px) от левого/правого края `#tabStrip`, `requestAnimationFrame`-цикл (`autoScrollStep`) двигает `strip.scrollLeft` на `SCROLL_SPEED` (8px) за кадр в сторону скрытых вкладок; останавливается на `dragend`/`drop`, а также на `dragleave`, если курсор действительно покинул `#tabStrip` (проверка `e.relatedTarget`, чтобы не сбивалось от вложенных `.tab`). Бейджи переполнения (`updateTabOverflow`) обновляются сами — программная установка `scrollLeft` триггерит нативный `scroll`, на который уже навешан этот хендлер. Нативный «призрак» перетаскивания (полноразмерный снимок `.tab`, который браузер по умолчанию рисует под курсором) в узкой панели наезжал на соседние элементы интерфейса (breadcrumb, тулбар). Вместо подавления — свой маленький drag image: `makeDragGhost(name)` создаёт компактный `<div class="tab-drag-ghost">` с названием вкладки, добавляет его в `<body>`, отдаёт в `e.dataTransfer.setDragImage(ghost, 14, 18)` и удаляет на следующий тик (браузер делает снимок синхронно в момент вызова `setDragImage`, поэтому элемент можно сразу убирать). `.tab.dragging` — простое затемнение (`opacity: 0.35`), как у задач/секций. Drag задач/секций в `#taskList` это не затрагивает — там используется нативный призрак без изменений. Сброс состояния (`endDrag()`) вынесен в общую функцию и вызывается явно из `drop`, а не только из `dragend` — успешный drop вызывает `moveTab()` → `renderTabs()`, которая пересобирает `innerHTML` `#tabStrip` и отрывает перетаскиваемый узел от дерева, после чего его `dragend` уже не всплывает до слушателя на `#tabStrip`; `dragend` остаётся резервным путём для отменённого drag (узел не удалён, событие всплывает нормально).
